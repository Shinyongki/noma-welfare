## 0. 배경

노마(사서원 대상 복지 안내·사건 처리 시스템)를 노인맞춤돌봄 수행기관용 연계 시스템으로 전환하는 중이다.

기관(산청)과의 실제 연계는 공모 마감 뒤로 미뤘다. 이번 작업은 **가상 데이터**로 한다.

### 완성 시 흐름

```
[1층 생활지원사]   어르신 선택 → 음성으로 상황 한 번 말하기 → 전달 완료
                                   (사업명·후보 표시 없음)
                                          ↓
[2층 전담사회복지사] 상황 + 대상자 이력 확인 → AI 추천 후보 확인(수동 선택 가능)
                   → 연계 요청 생성 → 내부: 수락/반려 대기 / 외부: 결과 기록
```

기존 노마의 구조(음성 대화 → AI가 서비스 판단 → 담당 부서 연결)를 둘로 나눈 것이다.
음성 입력은 1층으로, AI 판단은 2층의 **후보 추천**으로 옮긴다. 추천 대상은 사서원 부서가 아니라 연계처 목록이다.

## 1. 반드시 지킬 규칙

1. **범위는 이 지시서의 작업 2·4·5·3·6뿐이다.** 그 밖의 개선점은 고치지 말고 보고 목록에 적는다.
2. **각 작업은 `계획 보고 → 승인 → 구현 → 커밋·푸시` 순서로 진행한다.** 승인 전에는 파일을 수정하지 않는다.
3. **작업 1건이 끝날 때마다 즉시 푸시한다.** `git push origin pilot-sancheong`
4. `master`는 건드리지 않는다.
5. `.env`, 실제 명단, API 키는 커밋하지 않는다. `npm install`로 `package-lock.json` 등이 바뀌면 커밋하지 말고 보고한다.
6. 개인정보를 넣지 않는다. 대상자·기관·연락처는 누가 봐도 가상인 값만 쓴다. 담당자 개인 이름·직통번호 필드는 만들지 않는다.
7. `deptServiceMap`, `deptProfiles`, admin의 옛 부서 id 폴백은 작업 1에서 의도적으로 남겨둔 것이다. 외부 연계 대상 참조를 끊는 것 외에는 수정·삭제하지 않는다.
8. **1층 화면에는 사업명·신청방법·문의처·추천 후보를 어떤 형태로도 표시하지 않는다.** AI 응답도 1층에 보여주지 않는다.
9. **시스템은 연계 요청을 자동으로 생성·발송하지 않는다.** 추천은 추천일 뿐이고, 요청 생성은 항상 전담사회복지사가 누른다.

## 6. 작업 5 — 외부 연계 결과 기록 (신규)

**원칙**: 외부 연계는 접수가 시스템 밖에서 이뤄진다. 결과를 기록하지 않으면 외부 연계는 데이터에서 사라진다. 입력 항목이 늘면 현장에서 쓰지 않으므로 3개로 제한한다.

**변경 내용**

```
result: {
  accepted: boolean,     // 접수 여부
  agencyName: string,    // 기록 시점에 target.agencyName을 복사
  reason: string,        // 자유 텍스트. 분류 코드는 데이터가 쌓인 뒤 정한다
  recordedAt: string,    // ISO 시각
  recordedBy: string     // 현재 세션의 이름
}
```

- `result`가 `null`이면 미기록. 카드에 "결과 미기록" 표시
- referral 카드에 결과 기록 입력: 접수 여부(예/아니오), 기관명(target에서 미리 채움), 사유(선택)
- referral 카드의 진행·완료 버튼 제거. **결과 기록이 곧 완료다**
- 기록 후 수정 기능은 이번 범위가 아니다

**완료 조건**
- referral 1건에 결과를 기록하면 `result`가 위 구조로 저장되고 카드가 기록 완료로 바뀐다
- 기록하지 않은 referral은 "결과 미기록"으로 보인다
- referral 카드에 진행·완료 버튼이 없다

## 7. 작업 3 — 생활지원사 음성 입력 화면 (신규)

**원칙**: 생활지원사는 발견하고 전달한다. 어르신 댁에서 서서 쓰는 화면이므로 한 화면 한 동작, **3회 탭 이내**에 끝나야 한다. 연계 안내는 요건 판단과 사후 관리가 따라붙는 일이므로 2층의 몫이다. 책임이 따르지 않는 정보를 1층에 주지 않는다.

**기존 노마와의 차이**: 노마는 여러 번 주고받는 음성 대화였고 대화 중 사업을 안내했다. 이 화면은 **말하기 한 번으로 끝난다.** 음성 인식 부품은 노마 것을 재사용하고, 대화·안내·TTS 응답 부분은 가져오지 않는다.

**흐름 (3탭)**
1. 담당 어르신 선택 (탭 1)
2. 말하기 버튼 → 말이 끝나면 자동 종료 (탭 2)
3. 인식된 문장 확인 후 전달 (탭 3) → "전달 완료" 표시

인식된 문장을 보여주되 편집을 요구하지 않는다. 음성 인식이 실패하면 텍스트 입력으로 대신할 수 있게 한다.

**데이터 규칙**
- 케이스 1건 = 어르신 1명
- 생활지원사 보고는 해당 케이스 `notes`에 `type: 'field_report'`로 붙는다 (`text`, `createdAt`, `createdBy`)
- 대상자는 `scripts/seed_cases.mjs`로 사전 등록한다. **가상 대상자 3~5명**, 각 케이스에 담당 생활지원사 이름과 `sigun: '산청군'`을 둔다. 실제 명단 CSV는 커밋하지 않는다
- worker(생활지원사) 세션은 `/api/report/*`만 허용한다. 담당 어르신 필터는 세션 이름 기준
- 세션 저장소가 MemoryStore라 재배포 시 전원 로그아웃된다. 이번 범위에서 감수한다

**계획 보고 시 함께 보고할 것**
- 노마의 음성 인식이 무엇으로 구현돼 있는지(브라우저 Web Speech API / 서버 측 / Gemini) 와 재사용 방법
- 모바일 브라우저에서 동작 조건(https 필요 여부 등)

**완료 조건**
- 가상 생활지원사 계정으로 로그인해 어르신 선택 → 말하기 → 전달이 3탭 안에 끝난다
- 전달된 내용이 해당 케이스의 `field_report`로 저장되고 case.html에서 보인다
- 1층 화면 어디에도 사업명·신청방법·문의처·후보가 표시되지 않는다
- worker 세션으로 `/api/report/*` 외 API 호출이 거부된다

## 8. 작업 6 — 후보 연계처 자동 추천 (신규)

**원칙**: 시스템은 후보를 추천하고, 판단과 선택은 전담사회복지사가 한다. 추천은 요청을 만들지 않는다.

**변경 내용**
- case.html에서 `field_report`가 있는 케이스를 열면, 상황 내용과 **같은 화면에** 추천 후보를 최대 3건 표시한다
- 후보는 작업 4의 연계처 목록에서, **대상자 시군(`sigun`)과 같은 항목만** 대상으로 고른다
- 각 후보에 추천 근거 한 줄을 붙인다
- 후보를 누르면 외부 연계 생성 폼에 해당 연계처가 미리 선택된다. 요청 생성은 전담사회복지사가 버튼을 눌러야 이뤄진다
- 추천과 무관하게 목록에서 **수동 선택**도 그대로 가능하다
- AI는 노마의 기존 Gemini 호출 구조를 재사용한다. 입력은 `field_report` 텍스트 + 같은 시군 연계처 목록(`serviceName`, `eligibility`), 출력은 후보 `id`와 근거
- AI 호출이 실패하거나 키가 없으면 "추천을 불러오지 못했습니다"만 표시하고 수동 선택은 정상 동작한다
- 추천 결과는 저장하지 않는다(화면 표시용)

**완료 조건**
- 가상 `field_report` 1건에 대해 후보가 근거와 함께 표시된다
- 후보 선택 → 외부 연계 생성 폼 미리 채움 → 전담사회복지사가 눌러야 생성된다
- AI 실패 시에도 수동 선택으로 외부 연계를 만들 수 있다
