### 바뀐 구조 요약

- **승인자가 없다.** 기관 간 이동은 의뢰이며 요청 → 수락 또는 반려 2단계로 끝난다. 구 승인 API(`/api/dept/*`, `/api/target-dept/*`)는 410을 반환한다.
- **수락·반려는 받는 기관만** 한다. 서버에서 `session.deptId === linkage.toDept`를 검증하며, 관리자 세션에는 `deptId`가 없으므로 관리자도 403이다.
- **외부 연계(referral)는 생성 즉시 `accepted`**로 저장된다. 이메일·자식 케이스·원 케이스 상태 변경이 없다. 접수는 시스템 밖에서 이뤄지므로 결과를 `result`에 기록하며, 기록이 곧 완료다.
- **외부 기관은 시스템 사용자가 아니다.** 시스템은 연계처를 안내하고 결과를 기록할 뿐 연락은 전담사회복지사가 직접 한다.
- **1층(먼저봄)과 2층이 분리되어 있다.** worker 세션은 `/api/report/*` 밖으로 나가지 못하며, 1층에는 사업명·신청방법·문의처·추천을 표시하지 않는다.

PC 크롬 확인(로그아웃 / 권한 거부 전환 / 연계 문구)은 **결과 미기입 상태다.** 값을 받으면 이 표에 채운다.

확인 방식: `cloudflared`로 로컬 서버에 임시 HTTPS 터널을 열어 진행했고, 확인 후 터널을 닫았다. `tel:` 확인용으로 `data/linkage_targets_sancheong.json`의 `lt-002`에 가상 번호 `010-0000-0000`을 잠시 넣었다가 **원복했다.** 현재 연계처 5건은 전부 연락처가 빈 값이다.

### 알려진 한계

- **workerName을 로그인 시 직접 입력한다.** 다른 사람 이름으로 들어가면 그 담당 케이스가 보인다. 개인 계정이 없는 구조의 한계다.
- **크롬의 음성 인식은 녹음된 음성을 구글 서버로 전송해** 처리한다. 대상자 상황이 담긴 발화가 외부로 나가므로 실데이터 투입 전 검토가 필요하다.
- 공유 비밀번호 체계라 수락·반려한 사람과 요청한 사람이 구분되지 않는다. 기록되는 `by`는 기관명이다.
- 세션이 MemoryStore라 재배포하면 전원 로그아웃된다.
- `data/requests.json`이 git 추적 대상이다. 실데이터 투입 전 해결해야 한다.
- **기관별 열람 범위가 나뉘어 있지 않다.** 케이스에 소속 기관 필드가 없고 두 기관이 같은 서비스로 로그인하므로, 어느 기관으로 들어가도 명부 전체와 어르신 상세를 볼 수 있다. 실데이터 투입 전 해결 과제다(작업 7에서는 손대지 않음).

### 범위 밖 발견 사항 (손대지 않음)

- `CLAUDE.md:13`, `CLAUDE.md:122`, `docs/CLAUDE.md:8`의 모델 기재가 코드와 다르다. 문서는 "Gemini 2.0 Flash", 코드는 `gemini-2.5-flash`(`server.js:2219, 2430, 2493, 3211`)다.
- `admin.html`에 서버에 없는 라우트를 호출하는 코드가 남아 있다(`/api/admin/linkage/:id/approve` 등). 화면이 숨겨져 있어 실행되지 않는다.
- `POST /api/referral/:id/send`는 호출하는 화면이 없다. 라우트만 남아 있다.
- `git mv`가 이 환경의 권한 정책에 막혀, 시연 데이터 분리는 복사 후 원본 비우기로 처리했다. git 이력에 rename이 아니라 신규+수정으로 기록되어 있다.
